## 4. OFFICIAL POKÉAPI INTEGRATION

Use the official API:

https://pokeapi.co/api/v2/

Official documentation:

https://pokeapi.co/docs/v2

PokéAPI does not require an API key for its public REST endpoints.

Use only documented endpoints.

Required resources include:

### Pokémon List

GET /pokemon?limit={limit}&offset={offset}

### Pokémon Details

GET /pokemon/{id or name}/

### Pokémon Species

GET /pokemon-species/{id or name}/

### Pokémon Types

GET /type/{id or name}/

### Pokémon Generations

GET /generation/{id or name}/

### Pokémon Evolution Chains

GET /evolution-chain/{id}/

Optional for future expansion.

### Pokémon Abilities

GET /ability/{id or name}/

### Pokémon Moves

GET /move/{id or name}/

Before implementing each API feature:
1. Verify the endpoint exists.
2. Verify its current response structure.
3. Create appropriate TypeScript types.
4. Handle missing fields.
5. Handle nullable sprites and audio URLs.
6. Handle API errors.
7. Avoid unnecessary API requests.

Never invent API endpoints or undocumented query parameters.

Do not assume the list endpoint supports arbitrary searching, filtering, or sorting.

Implement such features using documented resources and client/server application logic.

### Data Fetching Architecture

Create a centralized API layer.

Examples:

- getPokemon()
- getPokemonList()
- getPokemonSpecies()
- getPokemonType()
- getPokemonGeneration()
- getPokemonEvolutionChain()
- getPokemonByIds()

These are application helper functions, NOT imaginary PokéAPI endpoints.

Use:
- Typed fetch wrappers
- Explicit error handling
- Request deduplication
- Bounded concurrency
- Appropriate caching
- Reusable error messages

Do not fetch details for every Pokémon in the entire Pokédex simultaneously.

Use pagination, incremental loading, or a lightweight searchable index.

Avoid excessive requests that could overload the public service.

### Sprite Handling

Prefer official sprite information returned by PokéAPI.

Support:
- Official artwork where available
- Default sprites as fallback
- Shiny sprites where supported
- Placeholder images when data is missing

Validate external image URLs.

Configure Next.js image handling correctly.

Use official artwork only from verified data fields.

### Pokémon Cry Handling

Read audio URLs from:

pokemon.cries.latest
pokemon.cries.legacy

Do not assume every Pokémon has audio.

Provide graceful fallback behavior for unsupported entries.

Do not hardcode undocumented audio paths.

## GAME 7: POKÉMON BATTLE SIMULATOR

Route:
/games/battle

### Important

This is a simplified educational battle simulator.

It is NOT intended to reproduce the full official Pokémon battle engine.

Clearly explain this limitation in the interface and README.

### Concept

The user chooses a Pokémon and battles an AI-controlled Pokémon.

### Gameplay

1. User selects a Pokémon.
2. Generate an eligible opponent.
3. Initialize combat state.
4. Display both combatants.
5. User selects an action.
6. Resolve turn order.
7. Apply damage.
8. Update HP.
9. Execute AI action.
10. Continue until a winner is determined.

### Combat Stats

Use actual PokéAPI base stats as input.

Create simplified derived combat values.

Example approach:

Max HP:
100 + baseHP * 2

Attack Power:
Based on the relevant base Attack or Special Attack

Defense:
Based on the relevant base Defense or Special Defense

Speed:
Based on the real base Speed stat

The exact formulas may be adjusted for balance.

Document all formulas.

Never present derived combat values as official Pokémon stats.

### Combat Actions

Implement three basic actions:

1. Quick Attack
   - Lower base damage
   - Higher action priority

2. Power Attack
   - Higher base damage
   - Lower priority or another clear drawback

3. Defend
   - Reduce incoming damage for the current turn

These are custom simulator actions, not representations of official Pokémon moves.

Do not claim they reproduce official move mechanics.

### Type Effectiveness

Determine an attacking type for applicable actions.

Use documented type damage relationships.

Support:
- Super Effective
- Normal
- Not Very Effective
- Immune

Apply appropriate multipliers.

For dual-type defenders, multiply both type interactions.

### Damage Formula

Implement a clearly documented simplified formula.

For example:

damage =
max(
  1,
  floor(
    (actionPower * attack / max(1, defense))
    * typeMultiplier
    * randomFactor
  )
)

Where:
- actionPower is defined by the simulator
- attack is a derived combat stat
- defense is a derived combat stat
- typeMultiplier comes from verified type relations
- randomFactor is a small bounded variation

If typeMultiplier is zero, damage must be zero.

Prevent invalid or negative damage.

### Turn Order

Determine action order using:
1. Action priority
2. Speed
3. Random tie-breaker

### AI

Implement basic decision-making.

The AI should:
- Choose among valid actions
- Consider type effectiveness
- Avoid obviously invalid actions
- Occasionally defend
- Not require an external AI service

Use deterministic pure functions where possible.

### Battle UI

Show:
- Pokémon sprites
- Names
- Types
- Current HP
- Maximum HP
- HP progress bars
- Action buttons
- Battle log
- Turn indicator
- Damage feedback
- Win/lose overlay

### Battle Rules

- No negative HP
- HP cannot exceed maximum
- No extra attacks after a Pokémon faints
- Prevent multiple actions during resolution
- Handle simultaneous or edge-case outcomes consistently
- Reset game state correctly

### Battle Result

Display:
- Winner
- Remaining HP
- Total turns
- Play Again
- Back to Games

Battle data is temporary.
